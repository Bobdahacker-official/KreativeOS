# ASRock A520M-HVS boot profile

Read-only Windows hardware inventory identified an ASRock A520M-HVS with firmware P3.50, an AMD Ryzen 5 4500 with 12 logical CPUs, 32 GiB of RAM, AMD xHCI controllers `1022:1639` and `1022:43ec`, an AHCI controller `1022:43eb`, and an ADATA Legend 800 NVMe drive. Windows reported UEFI Secure Boot disabled at the time of inspection. The profile uses xHCI and UEFI GOP. The QEMU launcher allocates 1 GiB of guest RAM. [ASRock motherboard specifications](https://www.asrock.com/mb/AMD/A520M-HVS/index.asp)

The NVMe drive can remain the Windows drive. The combined image boots from a dedicated USB device and stores data in its second partition. A normal Windows disk has no KreativeOS data marker. The kernel validates the exact partition layout before enabling writes and cannot issue filesystem writes to sector zero or the boot partition.

The motherboard has a Realtek RTL8111H Ethernet adapter. KreativeOS does not have a native RTL8111H driver. The QEMU profile presents RTL8139 to the guest and uses the host's network connection. Physical display uses UEFI GOP; there is no accelerated NVIDIA driver. The USB profile was designed for the detected controller class. It has not been booted on this physical motherboard.

## USB and filesystem design

The driver claims PCI xHCI controllers after firmware boot, negotiates device slots and endpoint contexts, and polls command, transfer and event rings. Boot protocol HID keyboards and mice and bulk-only SCSI mass storage work on directly connected root ports. Connect them before boot. The supported storage path is BOT, LUN 0, with 512-byte blocks. USB hubs, UASP and arbitrary HID report descriptors require additional drivers. [Intel xHCI specification](https://cdrdv2-public.intel.com/625472/625472_xHCI_Rev1_2b.pdf) · [USB HID specification](https://www.usb.org/sites/default/files/hid1_11.pdf) · [USB Bulk-Only Transport specification](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf)

The data volume uses exFAT 1.00 for portable files. It uses standard main and backup boot regions, directory entry sets, an allocation bitmap and an up-case table. The kernel verifies boot and entry checksums and flushes data and metadata before clearing the dirty flag. The firmware partition uses FAT for UEFI compatibility. The exFAT driver supports prepared KreativeOS images and a bounded root directory. A dirty volume must be checked outside KreativeOS before it can be mounted again. Ext4 uses different allocation and journal structures and is not implemented here. [Microsoft exFAT specification](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification) · [Linux ext4 documentation](https://docs.kernel.org/admin-guide/ext4.html) · [UEFI media access](https://uefi.org/specs/UEFI/2.10/13_Protocols_Media_Access.html)
